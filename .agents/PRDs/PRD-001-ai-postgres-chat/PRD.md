# Executive Summary

The AI PostgreSQL Chat Agent is a full-stack application designed to democratize data access within an organization. It allows non-technical and technical users alike to query a PostgreSQL database using natural language. By leveraging a sophisticated AI agent, the system translates user intent into safe, optimized SQL queries, executes them, and presents the results in an intuitive chat interface.

The value proposition lies in reducing the bottleneck on data engineering teams and providing instant insights to stakeholders. The MVP goal is to provide a functional chat interface that can handle basic to moderately complex read-only queries against a provided PostgreSQL schema with high accuracy and safety.

# Mission

To empower users to interact with their data as easily as they would in a conversation, ensuring data accessibility, security, and accuracy.

- **Data Sovereignty:** Ensure data remains secure and queries are strictly read-only by default.
- **Conversational Clarity:** Provide clear, human-readable explanations of the data retrieved.
- **Accuracy First:** Prioritize the correctness of SQL generation through robust validation and schema awareness.
- **Developer Experience:** Build a modular, extensible architecture that allows for easy addition of new data sources or agent capabilities.

# Target Users

- **Data Analysts:** Who want to quickly verify hypotheses without writing boilerplate SQL.
- **Product Managers:** Who need instant metrics on feature usage or user behavior.
- **Business Stakeholders:** Non-technical users who require data-driven answers for decision-making.
- **Developers:** Who want to explore a new schema quickly.

# MVP Scope

### In Scope
- [ ] Natural language to SQL translation using Pydantic AI.
- [ ] Read-only query execution against a PostgreSQL database.
- [ ] Chat-based user interface using React and shadcn/ui.
- [ ] Real-time streaming of AI responses.
- [ ] Schema exploration: The agent can "understand" the database structure.
- [ ] History of conversations.
- [ ] Basic SQL validation and safety checks (preventing DROP, DELETE, etc.).

### Out of Scope
- [ ] Write/Update/Delete operations on the database.
- [ ] Support for multiple database types (Postgres only for MVP).
- [ ] Complex multi-step data visualizations (charts/graphs beyond simple tables).
- [ ] User authentication and fine-grained access control (standard admin connection for MVP).
- [ ] Large-scale data exports (CSV/Excel).

# User Stories

- **As a Business User**, I want to ask "How many new users signed up last week?" so that I can report on growth without asking a developer.
- **As a Data Analyst**, I want to see the SQL query generated by the AI so that I can verify its logic before trusting the results.
- **As a Developer**, I want to ask about the schema (e.g., "What columns are in the 'aircraft' table?") so that I can understand the data model.
- **As a User**, I want to see a table of results for my query so that I can easily scan the data.
- **As a User**, I want the AI to explain the results in plain English so that I understand the context of the numbers.

# Core Architecture & Patterns

The application follows a standard full-stack architecture with a clear separation between the AI logic, the API, and the UI.

- **Backend:** FastAPI (Python 3.10+). Follows the RORO (Receive an Object, Return an Object) pattern and leverages dependency injection.
- **AI Layer:** Pydantic AI. Agents are defined with structured outputs and tools for database interaction.
- **Frontend:** React (Vite) with shadcn/ui. Uses React Router for navigation and follows Vercel React Best Practices to avoid waterfalls.
- **Database:** PostgreSQL accessed via `asyncpg`.

**Directory Structure:**
```
/backend
  /app
    /routers      # FastAPI routes
    /services     # AI Agent logic and DB interaction
    /models       # Pydantic models for API and Agent
    /core         # Config, DB connection, middleware
/frontend
  /src
    /components   # shadcn/ui and custom components
    /pages        # Application views (Home, Chat)
    /hooks        # Custom React hooks
```

# Tools/Features

- **Pydantic AI Agent:** Configured with a `system_prompt` containing schema information.
- **SQL Execution Tool:** A Pydantic AI tool that takes a SQL string, executes it via `asyncpg`, and returns the result set.
- **Schema Discovery:** A tool for the agent to query `information_schema` to learn about tables and columns dynamically.
- **Streaming UI:** Using `run_stream` from Pydantic AI to provide immediate feedback to the user.

# Security & Configuration

- **Read-Only Connection:** The application must use a database user with strictly read-only permissions on the target schema.
- **SQL Injection Prevention:** Use parameterized queries via `asyncpg`. The AI should generate queries, but execution must be handled safely.
- **Environment Variables:**
  - `DATABASE_URL`: Postgres connection string.
  - `OPENROUTER_API_KEY`: API key for OpenRouter.
  - `OPENROUTER_MODEL`: (Optional) Specific model to use (e.g., `anthropic/claude-3.5-sonnet`).
  - `LOGFIRE_TOKEN`: For observability.

# API Specification

- `GET /api/health`: Health check.
- `POST /api/chat`: Send a message to the agent. Supports streaming.
- `GET /api/schema`: Get an overview of the connected database schema.

# Success Criteria

- [ ] AI correctly translates 90% of basic natural language queries to valid SQL.
- [ ] Results are displayed in a responsive table in the UI.
- [ ] Response time for "thinking" and first token is under 2 seconds.
- [ ] No data modification queries (INSERT/UPDATE/DELETE) are executed.
- [ ] Logfire traces show full lifecycle of agent runs and tool calls.

# Implementation Phases

### Phase 1: Foundation
- Goal: Set up environment and basic connectivity.
- Deliverables: FastAPI skeleton, Postgres connection, Pydantic AI "Hello World" agent.
- Validation: Successful health check and DB ping.

### Phase 2: AI Agent & Tooling
- Goal: Implement the SQL agent and its tools.
- Deliverables: Agent with `execute_sql` and `get_schema` tools.
- Validation: Passing unit tests for SQL generation and execution.

### Phase 3: Frontend & Streaming
- Goal: Build the chat interface.
- Deliverables: Chat UI with streaming support, table rendering for data.
- Validation: User can type a question and see the result in the UI.

### Phase 4: Polish & Safety
- Goal: Robustness and UX.
- Deliverables: Error handling, SQL safety validation, Logfire integration.
- Validation: Attempted "DROP TABLE" fails gracefully; all runs logged in Logfire.

# Risks & Mitigations

- **Risk:** AI generates incorrect SQL (hallucination).
  - **Mitigation:** Display the generated SQL to the user for verification; use strict Pydantic models for SQL output.
- **Risk:** Expensive/Long-running queries.
  - **Mitigation:** Implement statement timeouts in Postgres and limits on returned rows.
- **Risk:** Prompt Injection.
  - **Mitigation:** Hardcoded read-only DB user; system prompt instructions to ignore data modification requests.
